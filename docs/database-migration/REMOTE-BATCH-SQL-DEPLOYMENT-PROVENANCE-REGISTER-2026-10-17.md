The marker describes a direct-to-production Supabase migration API batch, but the marker's heading/previous handover called this a **33-version batch**. A fresh parse of the marker's `Applied remote migrations` list found **35 distinct versions** (36 matching comment lines because `20260926102630 schoolpro_completion_security_cleanup` is repeated once in the header and once in the list). Therefore, **33 is not the number of distinct versions actually enumerated by the marker**; this discrepancy must be reconciled with the original deployment record before sign-off.

The marker intentionally omits DDL. The exact SQL payload for all 35 distinct versions has now been recovered directly from `supabase_migrations.schema_migrations.statements`, saved outside the executable migrations directory, and byte-compared with the saved GitHub files. The live ledger confirms each version/name as applied and records `created_by`; all 35 have a NULL `idempotency_key`. The ledger does not expose deployment timestamps, API request/response IDs or rollback payloads, so an independent API audit event is still unverified.

GitHub commit searches for representative original names (`schoolpro_admission_lifecycle`, `schoolpro_public_admission_and_candidate_cbt`, `schoolpro_completion_security_cleanup`, `schoolpro_new_tables_rls`) returned no original-source commit. The `statements` payload and creator are now preserved; no separate API request/response audit event with timestamp/result was recovered.
