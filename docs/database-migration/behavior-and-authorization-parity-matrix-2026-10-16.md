# SchoolPro behavior and authorization parity matrix
**Date:** 2026-10-16  
**Scope:** SchoolPro-only MySQL migration pilot; design and test planning, not production execution.  
**Status:** Initial control matrix. Source routine bodies, complete RLS expressions/grants, trigger ordering, deployed RPC versions and app call sites have not yet been fully captured, so no row below claims semantic parity.

## Evidence boundary

- Source catalog snapshot in [source-table-inventory-2026-10-16.md](./source-table-inventory-2026-10-16.md): 212 routines matching a targeted name filter, 358 trigger/event rows, and 293 RLS policy rows on SchoolPro-prefixed tables.
- Draft target schema: [database/mysql/001_schoolpro_core.sql](../../database/mysql/001_schoolpro_core.sql).
- Disposable MySQL 8.4 schema workflow #86 explicitly passed ten negative relational assertions, including the assessment-to-class-subject-assignment assertion. Each rejection was required to show MySQL ERROR 1452 and the expected named foreign key. This is structural integrity evidence only, not API authorization or semantic parity.
- This matrix translates known invariants into target responsibilities and required tests. It is not a substitute for exporting source definitions and tracing callers.

## Source evidence needed before implementation

1. Export complete definitions and signatures for relevant public/private routines, including overloads, owner, SECURITY DEFINER status, search_path, EXECUTE grants and dependencies.
2. Export every trigger on SchoolPro tables with timing, event, trigger function, enabled state, ordering and transaction implications.
3. Export all SchoolPro RLS policy expressions (USING and WITH CHECK), roles and table/sequence/function grants.
4. Trace all relevant .from(...), .rpc(...), Auth, Storage and Edge Function call sites in the SchoolPro repository, including server functions and scheduled jobs.
5. Capture source commit SHA, live catalog timestamp and deployed Edge Function version for each comparison.
6. Build disposable API-level contract tests. Database foreign keys alone do not prove authorization equivalence.

## Exit criteria for this matrix

A row can be marked **verified** only after (a) source behavior is captured, (b) the target behavior is implemented or an approved alternative is documented, and (c) a reproducible test demonstrates both allowed and denied cases. Do not mark the migration ready or use live customer data until all critical rows and the broader feature inventory pass review.
