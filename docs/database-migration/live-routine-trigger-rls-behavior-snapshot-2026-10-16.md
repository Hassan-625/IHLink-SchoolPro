## Source behavior confirmed from function bodies

- **Tenant relationships — `private.enforce_schoolpro_tenant_relations()`**: trigger function checks same-school student, subject and assessment scheme for `schoolpro_results`; same-school test/question for CBT question links; same-school test/student/class for CBT eligibility; and same-school template/student for document issues. It does not by itself cover every tenant relationship in the schema; additional trigger functions and RLS/foreign-key constraints participate.
- **Result total — `private.calculate_result_total()`**: BEFORE trigger uses `schoolpro_assessment_schemes.components` JSON, reads each component key/maxScore, treats a missing score as zero, rejects negative or above-max scores, and writes `new.total_score`. The MySQL draft instead models `assessment_components` and normalized `result_scores`; this is a material model difference that needs fixture-by-fixture parity, not a direct port assumption.
- **Published result workflow — `private.enforce_result_workflow()`**: blocks edits to selected assessment fields when the old status is `published`; role-gates status changes; stamps approval/publish timestamps. A separate `public.enforce_schoolpro_result_lock()` trigger also exists on results. The interaction and exact fields guarded by both must be reconciled before defining the target lock contract.
- **Lifecycle — `private.log_schoolpro_result_lifecycle()`**: AFTER UPDATE trigger appends an event when status changes for approval/publication/reopen/reject transitions, capturing the new row snapshot and `auth.uid()`. Verify event naming, event count, transaction rollback, and whether all status transitions need audit entries.
- **Student/class read gates — `private.schoolpro_can_read_student(uuid)` and `private.schoolpro_can_read_class(uuid)`**: require a signed-in user and active account; use school/operational status plus role and relationship checks (student identity, active guardian link, school owner, staff roles, teacher allocation/form-teacher relationships). The target API needs explicit allowed and denied cases for each relation, not a role-name-only mapping.
- **Result write/review gates — `private.schoolpro_can_write_result(uuid,uuid,uuid,text)` and `private.schoolpro_can_review_class(uuid,uuid)`**: result writes require active account and the results module, valid same-school student/subject, and a qualifying leadership role or teaching/coordinator relationship; review requires active account, operational availability, results and reports modules, a same-school class, and transcript/coordination authority. Full bodies and callers must be retained in the audit bundle for precise decision-table extraction.
- **Operational access / expiry — `private.schoolpro_operationally_active(uuid)` and `private.enforce_schoolpro_subscription_expiry()`**: active access requires active school + active subscription; the access function grants a 14-day extension only when amount > 0 and billing_cycle is annual. The expiry routine suspends expired `trial` subscriptions immediately at `renews_at`, while positive-price annual subscriptions receive 14 days. This appears inconsistent with the stated product requirement that demo is annual and also receives the two-week grace period. Treat this as a business-rule parity discrepancy to resolve in the target specification; no live policy was changed.
- **Progression/transcripts**: `schoolpro_bulk_academic_action` includes transcript issue, progression preview/apply paths; `schoolpro_archive_progression` records enrollment history and validates same-school student/class/session; `schoolpro_issue_transcript` snapshots student/session/term/subject result data; `schoolpro_revoke_transcript` records revocation metadata. These need idempotency, role, graduated/transferred, and historical integrity tests.
- **Finance triggers**: `schoolpro_auto_fee_invoices()` syncs invoices when fee structures/items change and prevents identity-changing a schedule once invoices exist. Preserve transactionality and retry/idempotency. Subscription routines enforce company finance/admin checks, lock invoice/submission rows, verify receipt object path ownership/existence and match the pending annual invoice before approval; port must preserve receipt-upload/manual-review flow and must not introduce BillStack.
- **Result/file access**: `schoolpro_result_access(...)` first calls student-read authorization and calculates finance/attendance-related result-release conditions. `schoolpro_family_report_media(text)` checks the requested object path against a published, locked result and student photo / term signatures / school result-template logo. Target storage API must authorize object ownership; never rely on a guessed file path.

## RLS observations from live catalog

Catalog baseline from the earlier read-only inventory: 293 RLS policy rows on SchoolPro-prefixed tables. Selected tables `schoolpro_classes`, `schoolpro_document_issues`, `schoolpro_fee_items`, `schoolpro_fee_structures`, `schoolpro_invoices`, `schoolpro_results`, `schoolpro_result_events`, `schoolpro_result_templates`, `schoolpro_students`, and `schoolpro_transcript_issues` need a full USING/WITH CHECK and grants review. The live query returned 46 policies across the eight core class/student/result/template/finance/event tables inspected in detail.

- `schoolpro_results` has permissive INSERT/UPDATE/SELECT policies plus restrictive SELECT gates using cached staff/family/reader scopes; UPDATE is explicitly restricted to draft, unlocked results and `schoolpro_can_write_result(...)`. Test permissive/restrictive policy combinations and cache invalidation as a whole.
- `schoolpro_students` and `schoolpro_classes` use restrictive scoped-read policies calling `schoolpro_can_read_student` / `schoolpro_can_read_class`, which are intended to narrow broader permissive policies. Preserve the restrictive intersection semantics in the API decision table.
- **Catalog review item:** `schoolpro_subscription_catalog` has a permissive authenticated SELECT policy named `schoolpro catalog readable` with `USING (true)` alongside policies that appear to limit reads to active plans. PostgreSQL permissive policies combine with OR, so the `true` policy can make inactive catalog rows visible to authenticated users unless another restrictive policy applies. Inspect table columns and intended visibility; treat this as a policy review item, not a proven exploit. Do not alter production policy in this migration pilot.
- For every table, export policy `USING` and `WITH CHECK`, `pg_class.relrowsecurity`/`relforcerowsecurity`, role/table/sequence/function ACLs, and view security settings. Policies alone do not show grants or function-wrapper exposure.
